*Stop treating AI like a science project. Start running it like a factory.*

In the early days of enterprise AI, data scientists were explorers. They requested hardware, downloaded models to their laptops, and ran experiments in isolation. Today, that model is broken. 

As demand for Generative AI explodes, the "ticket-based" workflow has become a severe operational bottleneck. Expensive GPUs sit idle at night while teams fight for capacity during the day. "Shadow AI" proliferates as frustrated developers bypass IT to use public APIs, leaking proprietary data.

**Models as a Service (MaaS)** in Red Hat OpenShift AI 3.3 is the answer. It is the shift from manual, static deployments to a **centralized, API-first utility**. MaaS enables you to define service tiers with different rate limits and quotas, control access through API key authentication, and track resource consumption for cost allocation.

== The Core Objection: "Why not just use a Public API?"

This is the first question every CTO asks: _"Why build this? Why not just point our developers to a public AI provider?"_

Public APIs are excellent for prototyping, but they fail at enterprise scale for three reasons:

 . **The Cost Explosion:** Public APIs charge per token. As you scale to thousands of employees and automated agents, costs become unpredictable. MaaS allows you to **cap your costs** by owning the compute and enforcing strict token quotas.
 . **The Privacy Gap:** Sending sensitive IP, PII, or financial data to a public endpoint violates Zero Trust principles. With MaaS, traffic never leaves your cluster, and access is governed by centralized authentication.
 . **The "Noisy Neighbor" Latency:** Public APIs offer no SLA on latency. MaaS gives you predictable performance by physically isolating workloads and offering advanced hardware optimization.

== The 3 Pillars of MaaS Value in RHOAI 3.3

Red Hat OpenShift AI 3.3 introduces a turn-key governance layer and advanced hardware capabilities to solve these enterprise challenges.

=== 1. Economic Efficiency (Solving "Idle Iron")
* **The Problem:** A single model rarely utilizes 100% of an expensive GPU. Dedicating one GPU per team results in wasted budget.
* **The 3.3 Solution:** **GPU Time Slicing & RoCE.**
OpenShift AI 3.3 maximizes hardware ROI through GPU time slicing, which enables multiple workloads to share a single physical GPU by dividing processing time. For massive models requiring multi-node setups, 3.3 introduces RoCE (RDMA over Converged Ethernet) with GPUDirect RDMA, enabling direct memory access between GPUs without CPU involvement for sub-microsecond latency.

=== 2. Turn-Key Governance (Solving the "Wild West")
* **The Problem:** Managing who has access to which model, and preventing a single runaway script from crashing the system.
* **The 3.3 Solution:** **Tier-Based Access Control.**
Through the integration of Kuadrant (Authorino and Limitador), RHOAI 3.3 introduces a strict tier system. Administrators can map OpenShift user groups to Default Tiers (Free, Premium, and Enterprise). These tiers mathematically enforce exact request rate limits and token consumption limits at the network edge.

=== 3. The Pathway to Agentic AI
* **The Problem:** Simple chatbots are no longer sufficient. Enterprises want to deploy autonomous AI agents that can securely interact with internal databases and execute multi-step tasks.
* **The 3.3 Solution:** **Standardized, Governed APIs.**
MaaS provides developers with an OpenAI-compatible API. By standardizing communication protocols (like the Model Context Protocol and Llama Stack API) within a governed, rate-limited environment, organizations can safely deploy intelligent autonomous agents without risking runaway compute costs.

== The Operational Divide: Who Does What?

Industrializing AI requires a strict separation of duties, which this course will cover:

* **The Cluster Administrator:** Handles the infrastructure. They enable the MaaS components, configure the Kubernetes Gateway API, and ensure Kuadrant is running.
* **The OpenShift AI Administrator:** Handles the business logic. They define the Service Tiers, assign user groups, generate API keys, and monitor token consumption for cross-departmental chargebacks.
