You have chosen the Distributed MaaS path. Now, let's look at the blueprint.

In OpenShift AI 3.3, a MaaS deployment is not a single container. It is a highly orchestrated, multi-layered distributed system. While the Gen AI Studio UI makes it look simple, a true GitOps architect must understand how the traffic flows, how the hardware is sliced, and how governance is enforced mathematically at the edge.

This section breaks down the 3.3 "MaaS Stack" layer by layer.

== Layer 1: Hardware Efficiency & Networking (The Base)

Before software touches a prompt, the infrastructure must be optimized. 3.3 introduces two major architectural patterns for hardware efficiency:

* **GPU Time-Slicing (For Scale-Out):** If you are running multiple smaller models (e.g., Granite-7B), dedicating a whole GPU to each is wasteful. By applying a specific `ClusterPolicy` and labeling the MachineSets, time-slicing allows multiple `llm-d` deployments to interleave their processing on a single physical NVIDIA GPU.
* **RoCE / GPUDirect RDMA (For Scale-Up):** If you are running massive models (e.g., Llama-3-70B) that require multiple GPUs spanning multiple physical worker nodes, standard TCP/IP networking creates a massive bottleneck. **RDMA over Converged Ethernet (RoCE)** allows a GPU on Node A to write directly to the memory of a GPU on Node B, bypassing the host CPU and achieving sub-microsecond latency.

== Layer 2: Disaggregated Inference (`llm-d` & `vLLM`)

This is the most significant architectural change in 3.3. You no longer route traffic directly to a `vLLM` pod. Instead, the inference workload is split into two distinct roles:

. **The Orchestrator (`llm-d`):** The Distributed Inference Server is the "brain." It receives all incoming requests from the Gateway. It understands the state of the KV Cache across all worker nodes. It performs **cache-aware routing**, ensuring that if User A asks a follow-up question, the request is routed to the specific worker node that already holds User A's context in its GPU memory.
. **The Workers (`vLLM`):** These are the "muscles." Deployed as stateful backend workers, they simply crunch the matrices and generate tokens as commanded by `llm-d`. 

By disaggregating these roles, the system can independently scale the prefill (processing the prompt) and the decode (generating the answer) phases, completely eliminating the "noisy neighbor" latency spikes that plague older architectures.

== Layer 3: Role-Oriented Networking (Gateway API)

To expose the `llm-d` engine, RHOAI 3.3 relies entirely on the **Kubernetes Gateway API**. This physically separates the networking responsibility:

* **The Cluster Admin** deploys the `Gateway` (the physical load balancer, IP address, and TLS termination).
* **The GitOps Pipeline** deploys an `HTTPRoute` that attaches the `llm-d` service to that Gateway. Developers never need cluster-admin rights to expose a new model.

== Layer 4: The Governance Plane (Kuadrant)

When an OpenShift AI Administrator uses the new 3.3 UI to create a "Premium Tier" with a limit of 10,000 tokens per minute, what actually happens?

The OpenShift AI Operator translates that UI action into declarative **Kuadrant** Custom Resources:

* **Authorino:** Enforces Authentication. It validates the MaaS API token generated by the user in the Gen AI Studio. If the token is invalid or missing, Authorino drops the connection (`401 Unauthorized`).
* **Limitador:** Enforces Quotas. It inspects the `x-ratelimit` headers. Crucially, it counts **aggregate tokens**, not just HTTP hits. 

By enforcing this at the network edge via Envoy WASM plugins, bad requests are dropped before they ever consume a single cycle of expensive GPU time.

== Summary: The 3.3 Request Lifecycle

To troubleshoot or engineer this system, you must understand the exact flow of a request:

1. **Client** sends an OpenAI-compatible POST request (`/v1/chat/completions`) using their MaaS API Token.
2. **Gateway API** receives the request at the edge of the OpenShift cluster.
3. **Kuadrant (Authorino)** validates the API token against the defined Service Tiers.
4. **Kuadrant (Limitador)** checks the token consumption math. _(If quota exceeded -> Returns 429 Error)._
5. **llm-d Orchestrator** receives the validated request. It checks its cache map and routes the prompt to the most optimal worker.
6. **vLLM Worker** executes the forward pass (leveraging RoCE if spanning multiple nodes) and streams tokens back to `llm-d`.
7. **Limitador** asynchronously updates the user's token usage in the backend database for chargeback monitoring.
8. **Client** receives the streamed response.
